# 현재 호스트를 알아내는 방법

이 문서는 **현재 기준서**다. 상태가 바뀌면 여기를 고친다.

조사 시점: 2026-09-12. 실제 운영 계정의 Server-to-Server OAuth 자격증명으로
직접 호출해 확인한 결과다.

## 1. 왜 필요한가

이 방은 호스트 권한이 **사람들 사이를 돌아다닌다.** 호스트만 화면 동시 공유,
호스트 열기/닫기 같은 관리 기능을 쓸 수 있으므로, 지금 그 권한을 누가 쥐고
있는지 알아야 한다.

전제가 되는 이 방의 성격은 다음과 같다.

- 24시간 열려 있는 고정 링크다.
- **마지막 한 사람이 나가면 회의가 종료된다.**
- 종료된 상태에서 링크로 들어오면 회의가 다시 시작된다.
  - 이 성질로 "최초 접속자 {이름} start~" 를 이미 구현했다 (`resolveOpener`).
- **최초 접속자가 호스트가 된다.**
- 호스트는 나갈 때 다른 사람을 지목해야 하고, **지목당한 사람이 새 호스트가 된다.**
- **나갈 때만이 아니다. 회의 중 언제든 다른 사람에게 호스트를 넘길 수 있다.**

마지막 줄이 이 문서의 핵심이다. **호스트 이양은 웹훅에 아무 흔적을 남기지 않고,
누가 나가는 순간에만 일어나는 것도 아니다.** 그래서 서버 쪽 신호만으로는 현재
호스트를 계속 따라갈 수 없다. 이 제약이 4절의 설계를 전부 결정한다.

## 2. 막힌 길 — 전부 실측으로 확인했다

### 2.1 웹훅 페이로드에 역할이 없다

백업 실데이터(`_backup/webhook-events.raw.ndjson`) participant 이벤트 157건 전수.

| 필드 | 채워진 건수 |
|---|---:|
| `public_ip`, `user_id`, `user_name`, `participant_uuid` | 157 |
| `leave_time`, `leave_reason`, `private_ip` | 103 |
| `join_time` | 54 |
| `participant_user_id`, `id`, `email` | **2** |

역할을 담은 필드는 없다. `email` 로 "방 주인 계정이면 호스트" 를 판정하는
우회도 불가능하다 — 157건 중 2건만 차 있고, 그 2건도 방 주인 계정이 아니다.

### 2.2 `host_id` 는 여전히 방 주인이다

`GET /meetings/{ZOOM_MEETING_ID}` 응답에서 `host_id`/`host_email` 은 방을 만든
계정 그대로였고 `status` 만 `started` 였다. `docs/webhook-data-reference.md` 의
기존 결론과 같다.

### 2.3 Dashboard(Metrics) live API — 플랜에서 막혔다

```
GET /metrics/meetings/{id}?type=live
GET /metrics/meetings/{id}/participants?type=live
→ {"code":200,"message":"This API is only available for ZMP and Business or
   higher accounts that have enabled the Dashboard feature."}
```

**스코프 문제가 아니다.** 발급된 토큰에는 `dashboard:read:meeting:admin`,
`dashboard:read:list_meeting_participants:admin` 등이 이미 전부 붙어 있다.
계정 등급이 Business 미만이라 막힌 것이다.

### 2.4 Report API(과거 회의)에도 역할이 없다

`GET /report/meetings/{uuid}/participants` 실제 응답 필드:

```
attentiveness_score, customer_key, duration, failover, groupId,
id, join_time, leave_time, name, status, user_email, user_id
```

### 2.5 역할 변경 웹훅 이벤트가 없다

Zoom Meetings 이벤트 목록에서 host/role 변경 이벤트를 찾지 못했다.
개발자 포럼에도 "참가자를 호스트로 바꿔도 웹훅이 오지 않는다"는 보고가 있다.
현재 구독 중인 이벤트는 `meeting.started`, `meeting.ended`,
`meeting.participant_joined`, `meeting.participant_left` 넷이다.

### 2.6 데스크탑 클라이언트 로그 긁기 — 암호화돼 있다

데스크탑 클라이언트의 회의 정보 패널에는 `호스트: {이름}` 이 그대로 나온다.
그 값을 로컬에서 빼낼 수 있을까 싶어 macOS 로그 디렉토리를 확인했지만,
`~/Library/Logs/zoom.us/` 에 남는 것은 `.zenc` 암호화 파일뿐이다.

> **그 패널 값은 회의에 접속한 클라이언트만 아는 값이다.**
> 서버 쪽(REST·웹훅)에는 애초에 존재하지 않는다.

## 3. 회의에 봇을 넣는 길

2.6 의 결론이 "회의에 접속한 클라이언트만 아는 값" 이라면, 클라이언트를 하나
만들어 넣으면 된다. Meeting SDK 봇이 그것이다. 처음에는 요금제와 승인 절차에서
막힐 것이라고 봤는데, **확인해보니 장벽이 없었다.**

### 3.1 요금제·권한 장벽은 없다

2026-03-02 부터 Meeting SDK 앱이 **외부 계정** 회의에 조인하려면 OBF 토큰과
앱 심사가 필요하다. 우리는 여기에 해당하지 않는다.

| 항목 | 우리 경우 |
|---|---|
| 조인 대상 회의 | **앱 소유 계정 내부** 회의 → OBF 면제 |
| 인증 | **JWT 하나**면 된다 |
| 마켓플레이스 게시·앱 심사 | **불필요** |
| Meeting SDK 사용료 | **무료.** 무료 플랜에서도 쓸 수 있다 |

전제는 하나다. **SDK 앱을 방 주인 계정(`techeer1`) 밑에 만들어야 한다.**
그 계정 회의에 붙는 것이 "내부" 의 정의다.

2.3 과 대조되는 지점이다. Dashboard API 는 계정 등급이 Business 미만이라
막혔지만, **Meeting SDK 는 등급을 보지 않는다.** 같은 계정으로 한쪽은 막히고
한쪽은 열린다.

### 3.2 "혼자면 40분 뒤 종료" 는 이 방에 적용되지 않는다

상주 봇의 전제가 되는 규칙이라 실측으로 확인했다. 백업 세션 `qS1TnTx8` 에서
한 참가자가 **09:04:58 부터 09:50:54 까지 약 46분간 혼자** 있었고, 회의는
끝나지 않았다. 그 사람이 나가고 **23초 뒤에** `meeting.ended` 가 왔다.

| 규칙 | 이 방에서 |
|---|---|
| 마지막 한 사람이 나가면 종료 | **맞다** (23초 뒤 `meeting.ended`) |
| 참가자가 1명이면 40분 뒤 종료 | **아니다** (46분 혼자 있어도 유지) |

라이선스가 할당된 계정이라 그런 것으로 보인다. 어느 쪽이든 **봇 하나만 남아도
회의가 유지된다**는 뜻이므로, 상주 봇은 기술적으로 성립한다.

### 3.3 상주의 대가 셋

성립한다고 해서 공짜는 아니다.

| 대가 | 내용 |
|---|---|
| **30시간 상한** | 회의가 영영 안 끝나므로 30시간마다 Zoom 이 강제 종료한다. 그 순간 회의 중인 사람이 **전원 튕긴다.** 지금은 방이 비면서 자연 종료되어 이 한계에 닿을 일이 없다 |
| **봇이 호스트를 선점한다** | 항상 봇이 첫 입장자이므로 **사람은 호스트가 되지 못한다.** 봇이 `ZoomMtg.makeHost({ userId })` 로 첫 사람에게 넘겨주는 로직이 필수가 된다. 운영 규칙 자체가 바뀐다 |
| **세션 경계 재설계** | 접속자 수로 세션을 다시 정의할 수는 있다. 다만 `meeting uuid` 가 더 이상 세션과 1:1 이 아니게 되므로, `meeting_uuid` 를 세션 키로 쓰는 **현재 스키마를 손봐야 한다** |

### 3.4 상위호환 — 사람이 있는 동안만 상주

세 가지 대가는 전부 "사람이 없을 때도 붙어 있는 것" 때문에 생긴다. 그런데
**사람이 없을 때는 호스트를 알 필요가 없다.** 그래서 이렇게 바꾼다.

1. `meeting.started` 웹훅 수신 → 봇 입장
2. 봇은 **두 번째 참가자**다 → 호스트 선점이 없다
3. 회의 내내 참가자 목록의 `isHost` 를 관찰 → 바뀌면 API 로 전송
4. 봇 외 인원이 0이 되면 → 봇도 즉시 퇴장 → **회의가 자연 종료된다**

| 3.3 의 대가 | 이 설계에서 |
|---|---|
| 30시간 상한 | 사라진다. 회의가 예전처럼 끝난다 |
| 봇의 호스트 선점 | 사라진다. 봇은 항상 두 번째다 |
| 세션 경계 재설계 | 사라진다. `meeting.started`/`ended` 와 `meeting_uuid` 가 지금 그대로다 |

얻는 정보는 상주와 **동일하다.** 웹훅 수신부터 봇 입장까지 5~15초의 공백이
있지만, 그 구간의 호스트는 첫 입장자로 확정이므로(4.1) 정보 손실이 없다.

엣지 케이스가 하나 있다. **마지막 사람이 나가면서 봇에게 호스트를 넘길 수
있다.** 봇이 호스트가 되면 — 사람이 남아 있으면 넘기고, 혼자면 나간다.

### 3.5 구현과 비용

| 갈래 | 평가 |
|---|---|
| 웹 Meeting SDK + 헤드리스 크롬 | 만들기 쉽다. `zoom/meetingsdk-web-bot-sample` 참고. 무겁다 |
| Linux 네이티브 SDK | 가볍다. 빌드가 고통스럽다 |

- 리소스: 헤드리스 크롬 1개당 대략 **1 vCPU / 1.5~2GB** 추정 — **실측 필요**
- 배치: Dokploy VPS 에 컨테이너 하나 추가하는 형태
- **Zoom 쪽 추가 과금은 없다** (3.1)

RTMS(봇 없이 WebSocket 으로 참가자 이벤트를 받는 방식)는 **크레딧 과금**이
필요하고, 호스트 역할 정보를 주는지도 미확인이라 현재는 후보에서 뺀다.

### 3.6 아직 검증되지 않은 것

이 절 전체가 다음 두 가지 위에 서 있는데, **둘 다 미검증이다.**

- 웹 SDK 의 `getAttendeeslist()` 가 실제로 `isHost` 를 채워주는지
- 회의 중 호스트가 넘어갈 때 SDK 이벤트가 오는지

**PoC 가 다음 단계다.** 여기서 막히면 이 절은 통째로 무효다.

### 3.7 인미팅 Zoom App 은 여전히 안 된다

역할이 포함된 `getMeetingParticipants` 는 **호스트/공동호스트만** 호출할 수
있고, 전원이 쓸 수 있는 `getUserContext` 는 자기 역할만 알려준다. 멤버 전원이
앱을 설치해야 해서 성립하지 않는다.

> **결론: 상주는 가능하지만 대가가 크다. 사람이 있는 동안만 붙는 형태(3.4)가
> 상위호환이다.**

## 4. 권장안 (아직 결정 전)

3절에서 봇 경로가 열려 있는 것이 확인됐으므로, **이 절은 "봇 없이 가는 경우" 의
설계다.** 3.6 의 PoC 결과에 따라 둘 중 하나를 고른다.

### 4.1 웹훅으로 알 수 있는 것과 없는 것

호스트 이양은 웹훅에 신호를 남기지 않는다. 그래서 웹훅이 줄 수 있는 것은
**처음 한 번의 값**과, **그 값이 더 이상 맞지 않는다는 신호**뿐이다.

| 상황 | 웹훅이 말해주는 것 | 확신도 |
|---|---|---|
| 세션 시작 직후 | 첫 입장자가 호스트 | **확정** (단, 그 순간만) |
| 그 뒤로 아무 일 없음 | 여전히 첫 입장자일 것 | **추정.** 조용히 넘어갔어도 알 방법이 없다 |
| 방에 한 사람만 남음 | 그 사람이 호스트 | **확정** |
| 호스트로 알던 사람이 퇴장 | 누군가에게 넘어갔다 | **불명** (후보 N명) |
| 세션 종료 | 리셋 | — |

"진짜 퇴장" 을 가리는 기준은 **`leave_reason` 이 아니다.** 소회의실 이동에도
`participant_left` 가 오는데, 실측상 방 이동의 **65%가 평범한 `left the meeting`**
으로 온다. 이유 문자열로 가르면 그만큼 틀린다.

실제 신호는 **발생 시각**이다. 방을 이동하면 같은 `participant_uuid` 에 대해
**동일한 발생 시각으로 `left` 와 `joined` 가 함께** 온다. 이미 `domain/presence.ts`
가 쓰는 규칙이고, 호스트 판정도 같은 규칙을 그대로 써야 한다.

```
같은 uuid · 같은 occurredAt 에 left 와 joined 가 둘 다  →  방 이동 (호스트 안 바뀜)
left 만                                                →  진짜 퇴장 (호스트 이양 가능)
```

### 4.2 그래서 자가 신고가 주(主)고, 웹훅은 보조다

처음엔 웹훅 추론을 주로 삼으려 했지만, 중간 이양이 가능한 이상 그럴 수 없다.
역할을 뒤집는다.

- **주: 자가 신고.** 화면에 **"지금 호스트는 저예요"** 버튼을 둔다. 호스트를
  넘겨받은 사람이 누르면 그 시점의 확정값이 된다. 상태 메시지 쓰기 경로와
  `ACCESS_TOKEN` 이 이미 있어 붙이는 비용이 거의 없다.
- **보조 1 — 초기값.** 세션이 시작되면 첫 입장자를 호스트로 세팅한다
  (`resolveOpener` 재사용). 아무도 버튼을 누르지 않아도 시작값은 맞다.
- **보조 2 — 무효화.** 다음 중 하나가 오면 현재 값을 버리고 불명으로 내린다.
  - 호스트로 알던 사람의 **진짜 퇴장**
  - **세션 종료**
- **보조 3 — 자동 확정.** 방에 한 사람만 남으면 그 사람이 호스트다. 신고 없이도
  확정된다. 이 방은 인원이 자주 1명까지 내려가므로(4.3) 생각보다 자주 걸린다.

버튼을 아무도 누르지 않으면 시스템은 조용히 틀린다 — 그래서 4.4 의 표기가 중요하다.

### 4.3 실데이터에서 확인한 것

백업 4개 세션에서 **첫 입장자가 실제로 나간 시점**과 그때 남은 인원이다
(이름은 익명화).

| 세션 | 이벤트 | 방 이동 | 첫 입장자 | 진짜 퇴장 시 남은 인원 | 그 시점 상태 |
|---|---:|---:|---|---:|---|
| CC/pxpN… | 33 | 11건 | A | 2명 | **불명** (후보 2명) |
| qS1TnTx8… | 15 | 3건 | B | 0명 | 세션 종료 → 리셋 |
| nkJ3q2io… | 4 | 0건 | C | 0명 | 세션 종료 → 리셋 |
| Ukm0EB9f… | 110 | 26건 | D | 1명 | **확정** (남은 1명이 호스트) |

주의: 이 표는 **무효화 신호가 언제 오는지**만 보여준다. 그 전까지 호스트가
그대로였다는 뜻이 아니다 — 중간 이양은 이 데이터에 아예 나타나지 않는다.

4개 중 3개는 끝까지 답이 나온다 — 둘은 방이 비면서 세션이 끝났고, 하나는 남은
사람이 1명이라 자동 확정된다. 후보가 갈리는 것은 한 세션뿐이다.

이 방은 인원이 0명까지 자주 내려가고, 그때마다 다음 세션의 초기값을 공짜로 다시
얻는다. **불명이 오래 지속되는 것은 사람이 계속 있는 긴 세션뿐이고, 버튼이 필요한
것도 거기다.**

### 4.4 화면 표기

확신도를 세 단계로 구분해서 보여준다. 이게 이 기능의 핵심이다.

```
호스트 OOO              ← 확정 (자가 신고 직후 / 남은 인원 1명)
호스트 OOO (추정)        ← 세션 초기값. 그 뒤 조용히 바뀌었을 수 있다
호스트 ? (후보 4명)      ← 불명
```

추정 상태는 시간이 지날수록 신뢰도가 떨어지므로 "OO분 전 기준" 같은 시각을
같이 보여주는 편이 낫다. 틀린 이름을 자신 있게 띄우는 것보다 모른다고 말하는
쪽이 낫다 — `resolveOpener` 가 "모르면 null" 로 짜여 있는 것과 같은 원칙이다.

## 5. 다시 볼 조건

- **계정이 Business 이상이 되고 Dashboard 기능이 켜지면** 2.3 을 다시 확인한다.
  단, 그때도 `metrics` 의 `host` 필드가 *현재* 호스트인지 방 주인인지는
  미검증이다. 붙이기 전에 실제 응답으로 확인할 것.
- Zoom 이 역할 변경 웹훅 이벤트를 추가하면 4절 전체가 불필요해진다.
  Marketplace 앱의 Event Subscriptions 화면에서 한 번씩 훑어보면 된다.
- **3.6 의 PoC 에서 `isHost` 관찰이 확인되면 4절 대신 3절 설계(3.4)로 간다.**
  자가 신고 버튼은 그때 불필요해진다.
- API 배포는 Dokploy 수동이므로, 여기서 나온 변경은 다른 API 변경과 묶어서 보낸다.

## 6. 재확인 방법

```sh
set -a; . ./.env; set +a
AT=$(curl -s -X POST \
  "https://zoom.us/oauth/token?grant_type=account_credentials&account_id=$ZOOM_ACCOUNT_ID" \
  -u "$ZOOM_CLIENT_ID:$ZOOM_CLIENT_SECRET" | jq -r .access_token)

# 2.3 Dashboard live
curl -s -H "Authorization: Bearer $AT" \
  "https://api.zoom.us/v2/metrics/meetings/$ZOOM_MEETING_ID?type=live"

# 2.2 방 주인
curl -s -H "Authorization: Bearer $AT" \
  "https://api.zoom.us/v2/meetings/$ZOOM_MEETING_ID"
```

`.env` 의 `ZOOM_ACCOUNT_ID`/`ZOOM_CLIENT_ID`/`ZOOM_CLIENT_SECRET` 는 현재 코드가
쓰지 않는다. 이 확인 용도로만 쓰였다.
