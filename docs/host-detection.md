# 현재 호스트를 알아내는 방법

이 문서는 **현재 기준서**다. 상태가 바뀌면 여기를 고친다.

**결론부터: 웹훅으로 해결된다.** `meeting.participant_role_changed` 가 그 시점의
호스트를 직접 지목한다. 봇도, 자가 신고 버튼도, 추정도 필요 없다.

조사 2026-09-12, 구현 같은 날.

## 1. 왜 필요한가

이 방은 호스트 권한이 **사람들 사이를 돌아다닌다.** 호스트만 화면 동시 공유,
호스트 열기/닫기 같은 관리 기능을 쓸 수 있으므로 지금 누가 쥐고 있는지 알아야 한다.

전제가 되는 이 방의 성격:

- 24시간 열려 있는 고정 링크다.
- 마지막 한 사람이 나가면 회의가 종료되고, 링크로 들어오면 다시 시작된다.
- 최초 접속자가 호스트가 된다(`resolveOpener` 가 쓰는 성질).
- 호스트는 나갈 때 다른 사람을 지목해야 하고, **나갈 때가 아니어도 회의 중
  언제든 넘길 수 있다.**

마지막 줄 때문에 "첫 입장자가 계속 호스트일 것"이라는 추정은 성립하지 않는다.
실제 이양을 알려주는 신호가 필요하고, 그 신호가 아래 2절이다.

## 2. 답 — `meeting.participant_role_changed`

이미 구독돼 있고 `webhook_events` 에 쌓이고 있었다. 2026-08-31 부터 258건,
31개 세션.

```json
"participant": {
  "user_name": "...",
  "old_role": "attendee",
  "new_role": "host",
  "date_time": "2026-09-12T07:48:19Z",
  "participant_uuid": "...",
  "participant_user_id": "..."
}
```

### 2.1 `old_role` 과 `new_role` 은 대개 같다 — 그래도 쓸 수 있다

| `old_role` → `new_role` | 건수 |
|---|---:|
| `host` → `host` | 186 |
| `attendee` → `attendee` | 60 |
| `co-host` → `co-host` | 11 |
| `attendee` → `co-host` | 1 |

변화량이 아니라 **그 순간의 역할**을 말하는 이벤트로 보면 된다. 그래서
`new_role = 'host'` 인 이벤트는 언제나 **그 시각의 호스트를 지목한다.**

이양 순간은 같은 시각에 오는 짝으로 드러난다.

```
09-11 15:04  B  host → host        B 가 호스트
09-11 15:28  F  host → host   ┐
09-11 15:28  B  attendee      ┘    F 로 넘어감
09-11 18:31  C  host → host   ┐
09-11 18:31  F  attendee      ┘    C 로 넘어감
```

### 2.2 무엇이 이 이벤트를 부르는지는 모른다

258건 중 **238건이 다른 이벤트와 ±2초 안에 겹치지 않는다.** 소회의실 이동이나
입퇴장이 트리거가 아니라는 뜻이다. 주기적 재확인으로 보이지만 규칙은 못 찾았다.

판정에는 문제가 되지 않는다 — 언제 오든 올 때마다 그 시점의 정답을 주기 때문이다.

## 3. 판정 규칙

`resolveHost()` (`apps/api/src/repository/query.ts`) 가 세 단계로 닫는다.

```
1. 마지막 new_role='host' 가 지목한 사람이 아직 접속해 있으면  → 그 사람
2. 그 사람이 나갔으면 — 남은 사람이 하나뿐일 때만              → 그 사람
3. 역할 이벤트가 없는 세션                                     → 문 연 사람(추정)
   그 외                                                       → null
```

**어느 단계에서도 못 정하면 null 이다.** 틀린 사람을 호스트라고 부르느니 모른다고
한다 — `resolveOpener` 와 같은 원칙이다. 화면은 null 이면 호스트 칸을 아예 그리지
않고, 3단계로 정한 값에만 "추정"을 붙인다.

`source` 필드가 근거를 밝힌다: `role_event` · `only_one_left` · `opener`.

### 3.1 실측으로 확인한 커버리지

| | 세션 수 |
|---|---:|
| `meeting.started` 가 기록된 세션 | 46 |
| 역할 이벤트가 있는 세션 | 31 |
| └ 호스트가 끝까지 있거나, 나갈 때 방이 비었다 | **30** |
| └ 남은 사람이 있는데 호스트만 나갔다(값이 상함) | **1** — 남은 인원 1명이라 2단계로 잡힌다 |
| 역할 이벤트가 없는 세션 | 17 → 3단계 |

즉 **역할 이벤트가 있는 세션은 31개 중 31개가 판정된다.**

### 3.2 방 이동을 퇴장으로 세지 않는다

호스트가 "나갔는지"를 볼 때 소회의실 이동을 퇴장으로 세면 안 된다.
`leave_reason` 으로 가르면 **방 이동의 65%를 놓친다**(평범한 `left the meeting`
으로 온다). 올바른 신호는 같은 `participant_uuid` · 같은 발생 시각에 `left` 와
`joined` 가 함께 오는 것이고, `domain/presence.ts` 가 이미 쓰는 규칙이다.

`resolveHost` 는 이 판정이 끝난 뒤의 참가자 목록(`isPresent`)을 받으므로 그
규칙을 그대로 물려받는다.

## 4. 막힌 길 — 기록으로 남긴다

전부 2026-09-12 에 실제로 호출해 확인했다. 다시 시도할 이유가 없다.

| 길 | 결과 |
|---|---|
| `host_id` | 회의방을 **소유한 계정**이라 방마다 고정. 오늘 누가 쥐었는지와 무관 |
| Dashboard(Metrics) live API | 스코프는 다 있는데 **플랜에서 막힘** — "Business or higher accounts" |
| Report API(과거 회의) | 응답 필드에 역할이 없다 |
| 데스크탑 클라이언트 로그 | `~/Library/Logs/zoom.us/` 는 `.zenc` 암호화 |
| 인미팅 Zoom App | 역할이 담긴 `getMeetingParticipants` 는 **호스트/공동호스트만** 호출 가능 |

### 4.1 봇은 왜 답이 아닌가

Meeting SDK 봇을 실제로 붙여서 확인했다. 요금제·심사 장벽은 없었다(앱 소유 계정
내부 회의는 OBF 면제라 JWT 서명만으로 붙는다). `getAttendeeslist()` 에 `isHost`
도 실제로 있었다.

**그런데 봇은 메인룸만 본다.** 사람들이 소회의실에 있던 시각에 붙여 보니 명단에
2명(봇과 메인룸의 한 사람)뿐이었고 **호스트는 보이지 않았다**. 같은 시각 웹훅은
호스트를 정확히 알고 있었다. 소회의실 명단은 SDK 내부 상태(`boRoomList`)에만 있고
공개 API 로 나오지 않는다.

여기에 상주 비용까지 얹힌다 — 30시간마다 회의 강제 종료, 봇이 첫 입장자가 되면
호스트 선점, 참가자 집계 오염, 24시간 도는 헤드리스 크롬.

**웹훅이 봇보다 우월하다.** 사각지대가 없고 비용이 0이다.

그때 만든 도구는 `poc/host-probe/` 에 **레거시로 남겨 둔다.** 다시 쓸 일은 없지만,
"봇으로는 소회의실이 안 보인다"는 결론의 근거가 그 안에 있다.

## 5. 이 조사에서 얻은 교훈

**우리가 이미 가진 데이터를 먼저 봤어야 했다.**

처음에 "역할 변경 웹훅 이벤트는 없다"고 결론 내렸다. 근거는 Zoom 공식 문서와
개발자 포럼이었다. 정작 `webhook_events` 테이블에는 그 이벤트가 12일치 258건
쌓여 있었다. `fixture` 와 `_backup` 은 이 이벤트를 구독하기 **전**(4월) 데이터라
4종밖에 없었고, 그것을 "웹훅에는 역할 정보가 없다"의 근거로 삼았다.

그 잘못된 전제 위에서 SDK 앱을 만들고, ZAK 를 뚫고, 봇을 붙이고, 40분 규칙과
30시간 상한까지 검증했다. 전부 불필요한 일이었다.

**외부 문서를 뒤지기 전에 운영 DB 를 본다.** 특히 "이 이벤트가 오는가"는
`select payload->>'event', count(*) from webhook_events group by 1` 한 줄로 끝난다.

## 6. 남은 한계

- 역할 이벤트가 없는 17개 세션은 문 연 사람으로 물러선 **추정**이다. 그 세션에서
  실제로 이양이 있었다면 틀린다. 화면에 "추정"이라고 밝히는 것이 지금의 답이다.
- 호스트가 나가고 여럿이 남으면 **null** 이다. 다음 역할 이벤트가 올 때까지
  모른다(실측상 31개 세션 중 이 상태로 끝난 것은 0개).
- 서버가 꺼져 있는 동안 온 역할 이벤트는 유실된다. 시각 공백 일반론은
  `docs/time-and-gaps.md` 를 따른다.

## 7. 재확인 방법

```sh
# 이 이벤트가 실제로 오고 있는가
select payload->>'event', count(*) from webhook_events group by 1 order by 2 desc;

# 지금 세션의 호스트 타임라인
select payload->'payload'->'object'->'participant'->>'date_time' as at,
       payload->'payload'->'object'->'participant'->>'user_name' as name,
       payload->'payload'->'object'->'participant'->>'new_role' as role
from webhook_events
where payload->>'event' = 'meeting.participant_role_changed'
order by 1 desc limit 20;
```

화면에서는 어드민 → **웹훅** 탭에서 `participant_role_changed` 로 걸러 보면 된다.
